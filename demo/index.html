Person A · data understanding & quality

The raw signal

METR-LA holds 34,272 readings for each of 207 sensors, from 1 March to 27 June 2012. Before any model, we checked that the file can be trusted: a SHA-256 fingerprint, no duplicate timestamps, no gaps in the 5-minute grid, no negative values.

The catch is that 8.1% of readings are exactly 0. A freeway at a true 0 mph for hours is rare, so we follow the DCRNN benchmark: a zero means "sensor did not report". Zeros are flagged, never filled in as a target, and never scored.

The curve is the whole network's mean speed by hour. The low point is 17:00 at 49.9, and the high is 22:00 at 63.0.

02
Person B · features & leak-free split

One hour in, four answers out

Every training example is a sliding window. The model sees the last 12 readings (one hour) and must predict the reading 1, 3, 6 and 12 steps later. From those 12 numbers we build 32 features: lags, rolling statistics, trend, time of day and missingness.

The split follows time: the oldest 70% trains, the next 10% tunes, and the last 20% is the exam, opened once. An example is kept only when all four of its targets fall inside the same split, so no answer leaks across the boundary.

03
Persons C, D, E · baselines, trees, fair scoring

Phase 1: every sensor on its own

Persistence says the future equals now. Historical average says the future equals the usual speed for this sensor, weekday and time. Both are honest bars to beat.

Random Forest averages many independent trees. XGBoost grows trees one after another, each fixing the last one's mistakes. Adding four historical-average features ("how far is now from normal?") gave XGBoost + HA, the Phase 1 winner at every horizon.

All five models were re-scored on the same 1.24 million test targets. At 60 minutes, XGBoost + HA cuts error by 31% against persistence (5.38 → 3.69).

Look at how the lines fan out. The further ahead you forecast, the more a single sensor's own past runs out of road.

Inside XGBoost

Trees added one at a time, each one fitted to what the others still get wrong.
Boosting, live toy

Fitted live in your browser on the 11 June curve, speed against time, using one-split trees and learning rate 0.3. The bottom strip is the newest tree's correction. The real model uses depth-8 trees on 32 features over 4.6 million rows, but the loop is the same.

  1. Start from one guess for everybody
  2. Measure what is still wrong: the residuals
  3. Fit a small tree to the residuals
  4. Add a shrunken copy of it: F ← F + η·tree
  5. Repeat until validation MAE stops improving
What the 60-minute model leans on real

The four historical-average features

Built from training data only (up to 23 May 2012, 07:05). ha_target is the usual speed for this sensor at the target's weekday and time. ha_delta is how much that usual speed changes between now and the target time. anomaly_now is how far the current speed sits from normal for right now. The fourth is the usual speed now. With these features, a 60-minute forecast can lean on "traffic tends to return to normal", which is exactly what the 32-feature model lacks.

Is the win real? The block bootstrap

Resample the 24 test days 2,000 times and see whether the gap ever closes.
Paired day-block bootstrap, run in your browser real data
  1. For each test day, sum each model's absolute errors at 60 min
  2. Draw 12 random 2-day blocks (with replacement, wrapping around): 24 days
  3. Recompute the MAE gap on that resampled set of days
  4. Repeat 2,000 times. The middle 95% of gaps is the interval
  5. If the whole interval sits above 0, the win is not luck

Days, not individual readings, are resampled, because readings within one day are strongly correlated. Blocks of 2 days keep some of that day-to-day correlation. The random draws here differ from the project's (numpy, seed 42), so the edges of the interval can move by a few hundredths. The official interval is shown for comparison.

The gap Phase 1 left open

A jam travels against the traffic

When a freeway clogs, the slow zone grows backwards, toward the cars still arriving. A sensor that only reads its own history cannot see the slowdown until it is already there.

Its downstream neighbour saw it minutes earlier. A graph model passes messages along the road links, so each sensor's forecast can use what the sensors around it are reading right now.

This animation illustrates the idea; it is not model output. Traffic flows left to right while the jam creeps right to left. Watch sensor C.

05
Members 1–4 · pipeline, GAT, DCRNN, controls, evaluation

Phase 2: let the road graph talk

The graph has 207 nodes and road-distance links, weighted by a Gaussian kernel of driving distance. Inputs become a tensor of 12 steps × 207 sensors × 7 channels: scaled speed, a missing flag, hour and weekday as sine/cosine, and a weekend flag.

GAT (Graph Attention Network) learns, for every sensor, how much to listen to each neighbour. DCRNN (Diffusion Convolutional RNN) spreads information along the road links in both directions inside a recurrent encoder–decoder.

To prove the road graph itself helps, we trained controls: the same models with only self-links (identity), with a shuffled graph (right degrees, wrong neighbours), and a GRU with no graph at all.

Result: the real graph wins clearly. A shuffled graph also helped GAT a little, so not all of GAT's gain comes from true road links. Hypothesis H2 was contradicted, and we report that.

Inside GRU local (the no-graph control)

A recurrent cell reads the hour step by step and keeps a running memory.
Unrolled over the 12 input steps untrained cell real input + forecast

Input is the section 02 window, scaled exactly as in training (mean 58.584, std 12.823). The cell has 8 units with fixed random weights so you can watch the mechanics. The real cell has 64 trained units. The forecast at the bottom is the trained model's real test prediction for this moment.

  1. Update gate z: how much old memory to keep
  2. Reset gate r: how much old memory to use for the new candidate
  3. Candidate ñ = tanh(W·x + r ⊙ U·h)
  4. Mix h ← (1−z) ⊙ ñ + z ⊙ h
  5. After step 12, a small head predicts the change from the last speed, for all 4 horizons

Inside GAT

Every sensor scores its neighbours, turns the scores into weights, and mixes their messages.
One attention layer at sensor — real neighbours

Neighbours are this sensor's real road links. The self-weight comes from the trained model's measured attention for this sensor; the rest of the weight is spread evenly over the neighbours for display.

  1. GRU encoder turns each sensor's last hour into a vector h
  2. Project it: Wh, split into 2 heads of 32
  3. Score each pair: e = LeakyReLU(a·Whᵢ + b·Whⱼ)
  4. Mask non-neighbours to −∞, keep the self-link
  5. Softmax over the neighbours gives weights α that sum to 1
  6. Weighted sum of messages, plus residual and LayerNorm
  7. Head predicts the change from the last speed for 4 horizons

Downstream and upstream overlap because most links run both ways, so they do not add up to the neighbour total. The histogram shows the self-weight for all 207 sensors, with the selected one marked.

Inside DCRNN

Information diffuses along the roads, hop by hop, inside a recurrent encoder–decoder.
Diffusion from sensor —, computed on the real graph real
Hops K Direction
  1. Forward transition Pf = Dout⁻¹ A: read the sensors you drive towards
  2. Reverse transition Pr = Din⁻¹ Aᵀ: read the sensors that drive into you
  3. Powers P¹ … Pᴷ reach K hops; each gets its own learned weights
  4. These graph convolutions replace the matrix products inside a GRU cell (DCGRU)

The map shows row i of Σ Pᵏ: how much the selected sensor reads from every other sensor. It is computed here from adj_mx.pkl, the same matrix the model was trained with.

Encoder–decoder, unrolled architecture

The encoder reads the 12 past steps for all 207 sensors at once. The decoder then steps 12 times into the future, and steps 1, 3, 6 and 12 become the 5, 15, 30 and 60-minute forecasts.

Member 5 · simulated signal control

From a forecast to a green light

Does a better forecast help a traffic signal? We simulated one signalised approach, driven by real test-period speeds from the 30 most congested sensors and by each model's real forecasts: 3,780 runs over 18 weekdays, 06:00–21:00.

The big win is adaptive versus fixed timing: from 2,179 seconds of mean delay per vehicle down to about 27. Which forecast feeds the controller matters far less. Even a perfect forecast saves only 0.40 s against XGBoost + HA.

Software only. Arrivals are generated from speed by an assumed rule. Nothing was tested on a real signal.

08
What we can and cannot claim

Limits, and how to run it

  • Units and clock. Speeds are in source units (likely mph). The timezone was never officially confirmed.
  • One city, one season. One chronological split, tested on June 2012. Intervals are not adjusted for multiple comparisons.
  • Maybe under-trained. GAT finals stopped at the 60-epoch limit and DCRNN at its 50-minute cap (14 epochs).
  • Not a fair graph test vs XGBoost + HA. XGBoost + HA gets historical-average features that the deep models do not.
  • Attention is not causation. Attention weights show what the model used, not how traffic really spreads.
  • Simulated signals. Every signal-control number comes from software.

Reproduce

Phase 1 files are frozen, and the Phase 2 scorer reproduces every Phase 1 metric exactly. Training took 11.2 hours on an Apple M3 (MPS). There are 107 Phase 2 tests.

pip install -r requirements-phase2.txt
python scripts/complete_phase1.py                    # Phase 1 end to end
python -m src.phase2.cli all --runs configs/phase2/runs_gat.yaml
python -m src.phase2.cli all --runs configs/phase2/runs_dcrnn.yaml
python scripts/phase2_eval_all.py                    # score everything
python scripts/phase2_run_signal_sim.py              # signal simulation
python -m unittest discover -s tests -p "test_phase2_*.py"
